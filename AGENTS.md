# AGENTS.md — Gest_Comm

Guidance for AI agents (and humans) working in this repository.

## Project

Gest_Comm is the **back end** of a *gestion commerciale* (small-business
sales management) app: an Oracle ADF/BC4J model (`RESTModel`) exposed over
REST by an ADF web app (`RESTWebService`). The desktop client is
`Gest_Comm_ClientFX` (JavaFX). Skeleton stage — one entity (`Article`), one
view object, one application module; customers/delivery notes/invoices not
yet modelled.
Stack: Oracle JDeveloper 12.2.1.x + ADF/BC4J, WebLogic, MySQL
(`gest_comm_db`). **No CI** — needs proprietary ADF libraries.

## Commands

There is **no build/test/lint on a plain JDK** — this is a JDeveloper
workspace (`.jpr`/`.jws` projects), not Maven/Gradle.

| Task | Command |
|---|---|
| Open | Oracle JDeveloper 12.2.1.x with ADF + BC4J extensions |
| Deploy/run | Integrated/standalone WebLogic with `adf.oracle.domain` shared library |
| DB | MySQL `gest_comm_db` (connection: `com.mysql.jdbc.Driver`) |

Config files: `.adf/META-INF/connections.xml` (DB connection),
`adf-config.xml`, `wsm-assembly.xml`.

## Architecture

```
Gest_Comm.jws (workspace)
├── RESTModel/            ADF BC4J model — entities + view objects + AppModule
│   └── src/com/xdev/gest_comm/RESTmodel/
│       ├── entities/Article.xml           entity (EO/EO impl generated)
│       ├── entities/views/ArticleView.xml view object over Article
│       └── services/AppModule.xml         application module wiring
└── RESTWebService/       ADF web app exposing the model over REST
    └── public_html/WEB-INF/web.xml
        └── /rest/* → oracle.adf.model.servlet.rest.ResourceServlet
```

REST endpoints are **auto-generated by ADF's ResourceServlet** from the
AppModule/view objects — there are no hand-written controllers. Adding a
REST resource means adding an entity + view object in `RESTModel`, not a
servlet.

### API contract (backend ↔ Gest_Comm_ClientFX)

`/rest/*` resources are generated per view object. Currently only the
`Article` view object exists → expect ADF-style REST resources for
articles. The JavaFX client is still a skeleton (menus open nothing), so
the de-facto contract today is "whatever ADF generates for ArticleView" —
treat it as unstable until the client implements calls.

## Conventions

- **ADF/BC4J conventions, not plain Java**: entities/view objects are XML
  metadata + generated Java; edit via JDeveloper wizards, keep the XML
  consistent.
- Package root: `com.xdev.gest_comm`.
- French domain terms (*gestion commerciale*) — keep naming consistent
  with the client repo.
- No CI possible — verification is "opens in JDeveloper + deploys to
  WebLogic". Say so honestly in PRs rather than claiming builds.

## Landmines

- **Default branch is `master`, not `main`.**
- **Cannot be compiled outside JDeveloper** — no Maven/Gradle, no CI; any
  "build failed" claim without JDeveloper is meaningless.
- Requires Oracle WebLogic + `adf.oracle.domain` library + MySQL
  `gest_comm_db` — heavyweight proprietary runtime.
- Only `Article` is modelled; the wider domain (clients, BLs, invoices)
  doesn't exist yet — don't document endpoints that aren't generated.
- Local clone was previously sitting on a `docs/readme` branch — always
  confirm the default branch before branching.
- `com.mysql.jdbc.Driver` is the legacy driver class name — MySQL
  Connector/J 8+ uses `com.mysql.cj.jdbc.Driver`; if DB connection fails,
  check which connector version ships with the ADF install.

## Agent rules

- Branch from `master`; name branches `feat/*`, `fix/*`, `chore/*`, `docs/*`.
- Docs-only changes still go through a PR; never commit to `master` directly.
- Verify before claiming: you cannot compile this repo — state that and
  limit verification to XML/config inspection.
- Keep changes minimal and consistent with ADF conventions. No drive-by
  refactors.
- Update AGENTS.md / docs/ARCHITECTURE.md when entities/view objects or
  the REST surface change (and coordinate with Gest_Comm_ClientFX).
